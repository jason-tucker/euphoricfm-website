## [0.3.0] — 2026-09-27 — WAV uploads

Members can upload WAV files as well as MP3s. The network-less probe converts a WAV to a CBR 320 kbps MP3, which replaces the WAV under the same upload id; everything downstream (prefill, review, finalize with ID3 + APIC, the AzuraCast upload, the library, edit and removal requests) is unchanged and only ever sees that MP3. WAV only (no FLAC, AIFF or M4A).

### Added
- **Probe WAV path** (`src/probe/wav.ts`, `probe.ts`). The type comes from the magic bytes of the probe's private copy (`RIFF....WAVE`), never from the name or the declared type; RF64 / BW64 (`wav_rf64_unsupported`) and RIFX (`wav_unsupported`) are refused. A bounded RIFF chunk walk runs in JS before any parser: every chunk inside the RIFF and the RIFF inside the file (a truncated file or a lying RIFF / data size → `wav_truncated`, more than 64 KiB after the RIFF → `wav_trailing_data`), at most 64 chunks, exactly one `fmt ` before exactly one `data`, a LIST ≤ 1 MiB whose INFO items tile it exactly (`wav_bad_list`; music-metadata reads every INFO value into memory), other chunks ≤ 16 MiB, at most one `id3 ` chunk, which gets the MP3 tag's pre-scan (≤ 5 MB, no compressed / encrypted frames). PCM only: integer 8/16/24/32-bit and float 32/64-bit, plain or WAVE_FORMAT_EXTENSIBLE with the PCM / IEEE-float GUID; ADPCM, MP3-in-WAV, A-law, µ-law, GSM and anything else are `wav_codec_unsupported`. 1–8 channels, 8–192 kHz, a consistent block align and byte rate, 30 s to 15 min. `ffprobe -f wav -protocol_whitelist file,pipe -threads 1` must agree with the header (one audio stream; only an `id3 ` APIC may appear as an attached picture; same channels, rate and duration ±1 s). music-metadata (heap-capped child, parser chosen by the copy's `.wav` name) pre-fills title / artist / album / genre / year from LIST/INFO and the `id3 ` chunk through the same `clipTag`; an APIC takes the same hardened cover path. The conversion is `ffmpeg -f wav … -map 0:a:0 -map_metadata -1 [-ac 2] [-ar 44100|48000] -c:a libmp3lame -b:a 320k -threads 1` under `prlimit` (256 MiB address space) → `timeout` (300 s) → `nice -n 19`, in its own process group. The MP3 is then checked like an upload (magic + second frame, no ID3, `ffprobe -f mp3`, exactly 320 kbps, duration within 1 s of the WAV's, ≤ 35 MB) before it replaces the WAV (tmp + rename, re-hashed); the cover is published last.
- **Upload caps by type.** New cap `maxWavUploadBytes` (250 MB; admins may lower it). The tus creation is capped by the type its Upload-Metadata `filetype` declares (audio/wav, x-wav, wave, vnd.wave → WAV; anything missing, malformed, repeated or else → MP3): the route checks the compiled limits (`413 upload_too_large` / `wav_upload_too_large`), `admitUpload` the loaded caps; tus `maxSize` is 250 MB. The probe request carries the loaded WAV cap (`maxWavBytes`, optional in the schema) and the probe caps by the ACTUAL type: an MP3 over 35 MB is `mp3_too_large` whatever it was declared as, a WAV over the WAV cap `wav_too_large`.
- **Staging accounting.** A WAV counts at its full length toward the per-user in-flight and the global staging caps; when the worker collects a converted result (`inputFormat: 'wav'`) it re-charges the upload row at the MP3's size in the same transaction as the item's move to pending. `items.input_format` records `mp3` / `wav` (migration `0006_v030_wav_input`).
- **UI.** The submit page accepts `.wav` / audio/wav / audio/x-wav / audio/wave, checks each file against its own type's limit, declares the type to tus, says "converting it to a 320 kbps MP3" while a WAV is checked, and shows "Converted from WAV (320 kbps MP3)" on the item (submit and review pages). Every WAV rejection code has a human message (`messages.ts`).

### Changed
- **A rejected upload's bytes are deleted at once.** On any refusal the probe unlinks the staged upload (and any cover it had published for it) and reports `released: true` (optional in the failure schema); the worker marks the upload `expired`, releasing its bytes from the staging quota. Before, a refused upload stayed on disk and counted toward the global staging cap for 7 days, which a 250 MB WAV would make a cheap way to fill staging. A failure without `released` keeps the old behaviour (an interrupted probe is released too, see Review fixes).
- The probe's `sha256File` and `publishFile` stream in 1 MiB steps (no whole-file buffers in the 256 MB probe) and `sha256File` no longer follows a symlink. `runLimited` takes an optional `nice` (1–19), placed between `timeout` and the tool (`/bin/nice`, busybox).
- An MP3 over 35 MB is now refused `mp3_too_large` after the magic check (it was `input_size` from the copy); `input_size` now means empty or over the hard 250 MB input cap.

### Review fixes (before release)
- **Bytes after the RIFF are checked, not skipped.** ffmpeg's wav demuxer ignores the RIFF size and parses chunks to the end of the file (music-metadata stops at the RIFF end), so an `id3 ` chunk (zlib bomb), a second id3 chunk, a LIST/INFO or `bext` appended after the RIFF reached ffmpeg unchecked. The chunk walk now runs to EOF: the ≤ 64 KiB after the RIFF must be all zero, or chunks under exactly the rules inside it (shared chunk count, single `fmt ` / `data` / id3 chunk, LIST/INFO tiling, id3 pre-scan); a header straddling the RIFF end counts as after it; anything else is `wav_trailing_data`.
- **One ID3 tag per `id3 ` chunk.** ffmpeg's ID3v2 reader keeps reading tags after the first (and skips over a header of an unsupported version by the length it declares, so a following chunk named `ID3x` could chain to an unscanned tag). The rest of the chunk after the tag must be zero padding, and the 10 bytes where ffmpeg looks for a next tag (after the tag, and after a v2.4 footer) must not look like an ID3 header, wherever they are (`wav_bad_id3`).
- **Interrupted jobs leave nothing behind.** At start-up the probe removes the per-job dirs (`p-` / `f-` / `a-`) a restart mid-job left in `staging/work` (a WAV job's private copy is up to 250 MB + the MP3, outside the staging quota). An interrupted in-web `probe` is now answered as a `probe` failure `interrupted` with its upload released (deleted before the result is written; nothing is done for a request that already has a result), so the worker marks the upload `expired` instead of holding its bytes until retention.
- **Unfinalized WAVs get their own reason.** A RIFF size of 0 / 0xFFFFFFFF or a data size of 0xFFFFFFFF (a file written to a pipe or by a live recorder, e.g. `ffmpeg … -f wav pipe:1`) is still refused, now as `wav_unfinalized` with a message that says re-exporting fixes it, instead of `wav_truncated`.
- **Size texts follow the loaded caps.** `upload_too_large` / `wav_upload_too_large` shown by the submit page carry the loaded (possibly admin-lowered) limits; the generic texts and `wav_too_large` no longer name a number. `interrupted` has a message.
- **Probe CPU weight.** `music-probe` gets `cpu_shares: 256` (cgroup v2 weight ~10 vs ~39 for a default container), so a conversion and the copy / hash / publish around it yield to the Discord bots; `nice -n 19` on ffmpeg only orders processes inside the probe's own cgroup.

## [0.2.2] — 2026-09-27 — v0.2.1 verification follow-ups

### Worker
Residual edge cases of the resumable archive / restore / re-verify (v0.2.1) where a song could need manual DB repair, or an older or failed snapshot could win over a newer successful change.
- **Stuck archive rows are settled by the portal itself (#1).** New mutating job kind `reconcile_archive` (in `JOB_KINDS`, `MUTATING_JOB_KINDS` and the request runner; scan window, pause and write gate as every other write). A scheduler sweep (every 10 min) queues it for `archiving` / `restoring` rows untouched for 30 min (new `archive.updated_at`, set on every status write and when a re-run resumes the row) that no queued or running `archive` / `restore` job will pick up. Where the file actually is decides: `archiving` with the file at `Removed/<id>/…` → the archive is finished (row `archived`, `after_archive` snapshot, re-verify; its removal request, even one the failed attempt already marked failed, is applied); `archiving` with the file still in the library → the snapshot memberships are merged back, the row is closed `failed` and an open request fails `archive_rolled_back`; `restoring` with the file still archived → back to `archived`; `restoring` with the file back → the restore is finished; anything else (media id gone, file elsewhere) → an alert naming the paths. Every outcome alerts.
- **Managers see and act on such rows (#1).** `GET /api/archive` and the Archived songs page list `archiving` rows too, with their `status`. New `POST /api/archive/:id/reconcile` (manage; `409 not_in_progress`, `409 archive_job_pending`) runs the reconciler now (**Resolve** button); `POST /api/archive/:id/restore` on an `archiving` row settles it first and then restores an archived song.
- **An open archive blocks other mutations of the song (#2).** While a media has an `archiving` / `restoring` row, `apply_edit`, `move`, `set_playlists`, `apply_art`, `reverify` and the ingest verify wait (`RetryLater` / `Defer`, no attempt spent, the default 7-day age bound) instead of editing, moving or repairing a half-archived song; the manager edit / playlist / art endpoints answer `409 archive_in_progress`. Since the reconciler closes stale rows, a later archive always starts with a new row and a fresh `before_archive` snapshot, never a closed attempt's. The archive rollback now MERGES the snapshot memberships (a REPLACE would drop memberships added since) and works wherever the file is in the library.
- **Events refusal on resume (#3).** A resumed archive repeats the `in_events_playlists` check before any further write: a membership outside the station set that appeared between attempts puts the snapshot memberships back, closes the row and refuses. The same check runs on the cleared state right before the move.
- **Only applied snapshots supersede (#4).** Supersede (re-verify chains and the ingest verify) and lost-row recovery consider only `after_*` and `ingest` snapshots (`APPLIED_SNAPSHOT_REASONS`); the `before_*` snapshot of an operation that then failed or was refused no longer marks older chains done unchecked, and recovery never re-applies it. `apply_edit` takes its `after_edit` snapshot also when it queues the folder move (the metadata change applied), so an older chain cannot revert it before the move runs.
- **First-sync playlist ids (#5).** The very first library sync marks every observed id that is neither assignable/default nor foreign as unconfirmed (so an admin can still move it to `foreign_playlist_ids`) and alerts once, like later syncs.
- **Orphan hint (#6, accepted residual).** An upload refused only by the time check (e.g. clock skew) is probably the item's own earlier upload: the alert now names that file (path and media id) and says to delete it by hand once the new upload is live.
- Migration `0005_v022_archive_reconcile` (`archive.updated_at`, default `now()`).
- Mock AzuraCast: `/__mock/az/station14` sets a file's Events (station 14) memberships, as that station's own UI would.

**Deploy note:** the first-sync change applies only while `station_playlist_ids` is still unset. If v0.2.1 already ran a library sync in production, the ids it classified silently stay confirmed; to make them movable to foreign, set `unconfirmed_playlist_ids` by hand to the `station_playlist_ids` values that are not in `assignable_playlist_ids` / `default_playlist_ids` (the sync keeps that list from then on). Do not reset `station_playlist_ids` to `null` on a live system: every playlist job fails `station_playlist_ids_unset` until the next sync.

### Web / probe / CI (PR #26 checks)
- **Request bodies are complete and the 1 MB cap is deterministic.** Next 15.5 runs Node middleware on a clone of the body and swaps the buffered copy into the request without awaiting it, so a handler that started reading while the body was still arriving lost its start: an oversized chunked body could answer 400 `invalid_json` instead of 413 (the CI flake), and a slow valid body 400. The middleware now reads its copy of every unsafe request's body to the end, counting it against the cap (413 `payload_too_large`, `Connection: close`), after the rate-limit and CSRF refusals; handlers keep their own caps. Regression test sends the body with a gap.
- **Probe children run without a shell.** `runLimited` execs `prlimit --as=<bytes> --core=0 -- timeout -s KILL -k 1 <s> <tool> <args...>` as a plain argv (same RLIMIT_AS / no-core limits as the former `sh -c 'ulimit ...'`); probe and test images add `util-linux-misc` (CodeQL js/shell-command-injection-from-environment).
- **Linear SVG sniff.** The cover SVG check is a cursor scan instead of a regex that backtracked exponentially on a run of comments (CodeQL js/redos; a 1 KiB head of `<!---->` hung the probe). A comment now ends at its first `-->`.
- **gitleaks:** repo-root `.gitleaks.toml` keeps the default rules and allowlists the verified false positives by exact path, on `generic-api-key` / `discord-client-id` only.

## [0.2.1] — 2026-09-27 — v0.2.0 verification fix round

### Worker
Fixes for the confirmed worker / AzuraCast findings of the v0.2.0 verification: ways a song could be silently lost from rotation, stranded in `Removed/`, attached to the wrong file, or have a manager's change reverted.
- **Ingest never adopts a row it did not upload (ING-1, SEC-4).** The target path is reserved (`ingest_runs.target_path` + new `upload_attempted_at`, DB clock) only after the window and pause checks, right before the POST. Other active runs' reservations count as taken in the collision walk (and a partial unique index on `ingest_runs.target_path` for non-terminal runs backs it). A retry adopts the row at its reserved path only when it is provably its own upload: attempt marker set, a scanned media row whose file size equals `final.mp3`'s, uploaded no earlier than the attempt, length within 2 s of the probe duration when known, and no other item or run holding the media id; anything else is audited, alerted and skipped (the next ` (n)` name is used).
- **Archive is resumable (ARC-1, ARC-2).** An `archive` row with status `archiving` and the `before_archive` snapshot is written before the first AzuraCast write; a re-run reuses that snapshot and continues from where the file really is. A move whose reply is lost (timeout, failed verify read) finishes the archive when the file is at `Removed/<id>/<name>`; only a verified not-moved file is rolled back (and the row closed as `failed`).
- **Restore is resumable (RES-1).** Status `restoring` is written before the move; a re-run with the file already at its original path (same `unique_id`) skips the move and continues with metadata, memberships (merged), verify and the status flip. `Restore` is offered for `restoring` rows.
- **Re-verify never reverts newer changes (VER-1).** A reverify re-applies its snapshot only while it is the latest portal snapshot of the media (else it is marked superseded and the request done), re-adds missing playlist ids by merge (never a REPLACE with an old set), and counts extra memberships as fine. `set_playlists` now takes an `after_playlists` snapshot and runs its own reverify chain. Lost-row recovery uses the latest snapshot. The ingest verify and repairs merge too, and a portal mutation of a still-verifying song supersedes the ingest verify (the song goes live) instead of being treated as lost.
- **Events playlists (ARC-3).** A song with a membership in any playlist outside the station-1 set (the Events station 14) is refused before anything changes (`in_events_playlists: <ids>`, and the ticket says to take it out of those playlists first); the "cleared" check counts station-1 memberships only. `foreign_playlist_ids` default is now `[74, 75, 76, 77, 78]` (live DB).
- **Station playlist ids are sync-owned (SET-1).** `station_playlist_ids` is read-only in the admin UI/API; `foreign_playlist_ids` is the admin control. The sync never shrinks the set by observation; a newly seen id that is neither known nor foreign is counted as station 1, alerted once and recorded in `unconfirmed_playlist_ids`. Admins cannot mark an assignable/default or a confirmed station-1 id foreign, nor make a foreign id assignable.
- **Waits (JOB-1, F1).** Scan-window and pacing waits are `exact` (no 30-minute age floor that phase-locks old jobs onto the closed window). A wait that ages out now fails its request (`failRequest`, `wait_expired`, ticket post) or item (`failIngest`) instead of only killing the job; window / on-air / pacing and the ingest job's own waits get an explicit 40-day bound (past the 30-day artist wait), `ingest_verify` keeps 7 days.
- **Smaller fixes.** A manager's direct edit carries the artist the manager saw (`beforeArtist`), so a retry after the metadata PUT still queues the folder move (EDIT-1). Recovery remaps queued jobs' `payload.mediaId` in the same transaction (REMAP-1). An edit whose new artist sanitizes to another artist's folder (active, pending or denied) fails with `artist_folder_taken` instead of merging into it (SEC-5).
- **Album-art verify (ART-1).** The wrapper gains a read-only, station-checked `GET /api/station/{id}/art/{media_id}` (`getArt`, never follows the generic-image redirect; the path is already in the contract drift probe). `apply_art` stores the old art's sha256 in the `before_art` snapshot and, after the upload, requires the served art to be the probe JPEG or a complete JPEG with the probe's dimensions (AzuraCast re-encodes).
- Migration `0004_v021_worker` (`archive_status` += `archiving`, `restoring`; `ingest_runs.upload_attempted_at`; the two partial unique indexes). It fails if two active runs already share a `target_path` or a media has two open archive rows.
- Mock AzuraCast: Events playlists 74–78 are station 14's (the playlist REPLACE keeps exactly those); list entries report the file size; uploads get a real `mtime`/`uploaded_at`; stored art is re-encoded when its header is readable; `/__mock/az/ignore-next-put` (a metadata PUT that reports success without storing; F2 test).

### Web / probe / deploy

#### Security
- **Album-art uploads cannot exhaust music-web's memory (SEC-1).** `POST /api/uploads/art` now takes an in-flight slot (1 per member, 3 per process; `429 art_upload_in_progress` / `503 art_uploads_busy`) and runs the quota pre-check before reading any body byte; those refusals, like the route's earlier ones (rate limit, sign-in, uploads paused) and every CSRF refusal, carry `Connection: close`. The body is read into one buffer of its `Content-Length` (required: `411 content_length_required`; still ≤ 5 MB + 64 KB) and the single multipart file part is parsed in place (`server/art/multipart.ts`) instead of through `Response.formData()` + `File.arrayBuffer()` (about four copies per request before). A body still incomplete after 120 s is `408 body_timeout`, a disconnect ends the read, and the slot is released in `finally`. Worst case about 15 MB of art bodies in flight.
- **Album-art caps (SEC-2).** Per member per rolling 24 h: 30 uploads and 50 MB (`429 art_daily_quota`); globally 512 MB of processing + ready art (`503 art_storage_full`). Art bytes (processing, and ready JPEGs kept 7 days, charged at the uploaded size) now count toward `maxStagingBytes` for both art and tus admissions, all under the one staging advisory lock; the art row is inserted by that locked admission before the raw file is written, and any later failure (file write, audit, spool request) marks it rejected and removes the raw file (best effort, never masking the original error). New caps `artUploadsPerUserPerDay`, `artBytesPerUserPerDay`, `maxArtBytes` (admins may lower them; optional in the admin schema so older saved caps stay valid).
- **One metadata character rule (SEC-3).** `PATCH /api/items/:id` uses the edit-request rule (`requests/common.ts` `metaText`: NFC, trimmed, length counted after NFC, no `\p{Cc}` incl. `\n`/`\t`, no `\p{Cf}`, no U+2028/U+2029). A newline or tab accepted here used to fail finalize after approval (`bad_finalize_request`), and bidi / zero-width characters reached the on-air ID3. The probe's pre-fill (`probe/tags.ts` `clipTag`) turns controls and separators into a space, drops `\p{Cf}`, applies NFC and never cuts a surrogate pair, so an untouched pre-fill always finalizes.

#### Deploy
- **`MUSIC_APP_DB_PASSWORD` must be URL-safe (F1):** 24–128 characters of `[A-Za-z0-9_.-]`; `/`, `+` and `=` (base64) are refused because the same value goes into `DATABASE_URL`. Generate it with `openssl rand -hex 24`. **Upgrade note:** a deployment whose password contains `+` or `=` (which the URL tolerated) must rotate it in `migrate.env`, `web.env` and `worker.env` before this migrate step runs.
- **First boot cannot race initdb (F2):** the `music-db` healthcheck uses TCP (`pg_isready -h 127.0.0.1`), which the entrypoint's socket-only initdb server does not answer, and `music-migrate` retries its first connect for up to 60 s on "not reachable / starting up" errors only (a bad password or SQL error still fails at once).


## [0.2.0] — 2026-09-27 — Integrated portal: P3 ingest, P4 requests, UI, album art

One deployable build: the P2 foundation (0.1.1) with P3 (`feat/music-ingest`), P4 (`feat/music-requests`) and the UI (`feat/music-ui`) merged. P5 (SoundCloud) is not included. Where the branches overlapped, the foundation's version was kept.

### Added
- **Review and ingest (P3).** New-artist items (one per unknown main artist, created at submit) and their approval with a reviewer-confirmed folder from the strict sanitizer; `PATCH /api/items/:id` metadata overrides; `attestVersion` recorded with the attestation; year in the probe prefill. Approving a song enqueues `ingest`: artist gate → probe `finalize` (effective cover) → worker re-hash → scan window + pacing (≥ 90 s, ≤ 6/h) → path build + collision walk → upload → playlists → verify + snapshot → post-scan re-verify → `live`, with lost-row recovery. `library_cache` sync every 10 min (artist seeding, `station_playlist_ids`, `art_url`), per-item ticket posts (live / failed), the batch summary with `completed`, 7-day auto-close, final-file cleanup through the probe (`cleanup_final`), an optional Kuma disk push, and a behavioural `/files/batch` contract check.
