# Changelog — EFM Music Portal (`music/`)

## [0.5.3] — 2026-09-29 — Events: one-page request form that saves itself, inline uploads

Member feedback on events.euphoric.fm: songs added to a draft were lost ("adding songs didn't stay in during a draft save"), announcements had to be uploaded on a separate page, and the form should be one page that saves automatically. Root cause of the lost songs: the step wizard saved the playlist only when leaving the playlist step with a fully valid playlist, so songs added before a valid Continue lived only in the page's memory (production draft 3: details saved, 0 tracks, no playlist-save audit row).

### Changed
- **The request is one page** (`/request`, and `/my/events/:id` for your own draft): Details · Date & time (ET/Local inputs, 24 h minimum, 48 h short-notice warning, the day's bookings and the clash check) · Visibility · Songs (library search, add/remove, Up/Down, shuffle or your order, pins) · Announcements (EFM set or your own audio, at a time or on repeat) · Review & submit (summary, the rules, Submit). A row of section links sits at the top. The step wizard (`RequestWizard`) is gone; the details / time / visibility fields, the playlist builder and every validation message are the same components as before. Pending, approved, built and live events keep the editor with explicit saves (a pending request's every save posts the changes to its ticket; an approved event's edit asks to confirm the re-approval first; live-event restarts still need staff confirmation).
- **Autosave** (`src/events/components/autosave.ts`): every change is backed up on the device (localStorage `efm_ev_form:<discord id>:new` for a new request, `efm_ev_form:<discord id>:<draft id>~<tab>` per tab for a draft, read and written in try/catch) and restored on the next load while it holds changes the server does not have ("We restored changes you made on this device…", with "Use the saved version instead" for a draft and "Start over" for a new request). The draft is created on the server as soon as it has a valid title, kind, time and visibility; until then the status says "Draft not saved yet — add …". After that the form saves ~1.5 s after the last change: PATCH of the changed valid details and PUT of the playlist, both with the loaded `version`, `expectStatus: "draft"` and a random `saveId` (see Fixed below). Saves are serialised (never two in flight) and edits made meanwhile are coalesced into the next save; a `409 version_conflict` re-reads the event and merges it into the form (see Fixed below); network errors, 408/425/429 and 5xx retry with backoff (2 s doubling to 30 s); leaving or hiding the page sends the last changes with `fetch(..., { keepalive: true })` as one combined request (see Fixed below). Invalid fields (an empty title, a time that breaks a rule) are not sent and stay on the device with a message. A new draft moves the page URL to `/my/events/<id>`, so a reload opens it. The status shows near the top (announced with `aria-live`) and next to Submit: "Saving…", "All changes saved ✓ <time>", "Not saved: <reason> — retrying", "Offline — saved on this device". Submit first sends every pending change, then submits.
- **Draft playlists save even while a timing rule is broken.** `PUT /api/ev/events/:id/playlist` on a **draft** (and a draft's time change) checks only what makes the rows valid: every song, stinger and upload id exists and is the owner's, no song twice, a length for every announcement. Pin and announcement windows, the nightly-restart band and the row cap are checked at **submit**, which always ran the full check. The form still shows these problems live and blocks Submit until they are fixed. Pending, approved, built and live events keep the full check on every save.

### Fixed (found in review, before release)
- **A fresh upload blocked every save of the draft for several minutes.** The form offered an upload as soon as it was "ready", but a few seconds later the worker moves it to "ingesting" (being copied into AzuraCast, often 7 minutes or more), and the API only accepted "ready" or "live": every save then failed with `audio_not_ready` until the copy finished. The API now accepts **ready, ingesting and live** (`AUDIO_USABLE_STATUSES`) for a draft save and for submit; the build still waits for "live" and fails the build with `audio_not_ready` if it is not there by then. The form, the inline upload and My audio use the same list, so "still being checked" (probing) is never selectable and rejected/failed never are. If a save is still refused with `audio_not_ready`, the song stays in the form and on the device, the status says "One of your uploads is still being checked. It's added to the draft by itself once it's ready. — retrying", and the save retries by itself (with backoff, and at once when the upload list shows the file ready).
- **Two tabs on the same draft overwrote each other.** A tab that was behind re-sent its whole form after a `409`, wiping the other tab's saved changes (seen in testing: tab A's host name and a song vanished when tab B saved). Now each tab remembers the server copy it last loaded or saved, and a newer server copy is **merged** (`src/events/components/merge.ts`): details this tab did not change take the server's value, details it changed keep its value and only those are sent; songs become the server's list minus the songs this tab removed plus the ones it added (a song both added is there once; a pin this tab changed wins); announcements the same by content, never doubled; the play order is this tab's if it changed it. The form then shows the merged result with a short note that names what came in from the other tab and any field both tabs changed ("Merged changes made in another tab: host name → "Host From A" and added "Bravo". Kept this tab's title."). A tab also catches up by itself when it comes back into view (focus / visible) and shortly after another tab's device copy changes, without sending anything unless it has changes of its own. If the draft was submitted or withdrawn in the other tab, this tab stops saving and says so instead of editing the request. Each tab keeps its own device copy (with the server version and copy it was made against), so tabs never overwrite or clear each other's copies; on the next load every copy is merged into the current server copy the same way, never written over it (a copy whose changes already arrived restores nothing and is removed). The keepalive sent on leaving carries only this tab's changed fields, its base version and the draft status guard, so a stale one is refused (`409`) and its changes wait in the device copy for the next load.
- **A tab left open on a draft could change the request after it was submitted or approved** (found in the second review). Submitting and approving do not change the event's version (the worker keys builds by version), so a second tab still showing the draft passed the version check: its autosave was accepted, sent the approved event back to Pending, queued a teardown of its station build and posted to the ticket, while the tab still said "All changes saved". Now every autosave (and the keepalive) sends `expectStatus: "draft"`, and `PATCH /api/ev/events/:id` and `PUT /api/ev/events/:id/playlist` refuse an edit whose `expectStatus` differs from the event's status with `409 status_changed` (the body names the current status), checked under the same row lock as the version, so nothing is written, queued or audited. "Discard draft" sends the same guard to `POST …/withdraw`, so it can never withdraw a request that was submitted meanwhile. The tab also checks the status on every copy of the event it reads (even when the version is the same) and stops for good, saying "This request was submitted (and approved) in another tab or on another device, so this page no longer saves. Your latest changes on this page were NOT saved." with a link to reload the request. The explicit editor for pending, approved, built and live events (members and staff, and the staff visibility switch) sends the status it loaded, so a change confirmed against "Pending" cannot land on an event approved meanwhile: it is refused, the page reloads the event and says the change was not saved. Device copies of a draft are never applied to a request that is no longer a draft: its page lists the unsaved changes briefly ("Some changes made on this device had not reached the draft when the request was submitted, so they weren't saved: …"), discards them and sends nothing.
- **A save sent as a tab closed could, on the next load, undo newer changes made elsewhere.** When a tab closed within 1.5 s of an edit, the keepalive save arrived but the tab's device copy stayed; on the next load that copy counted as unsaved changes against its old base and was merged in and saved, overwriting a host name changed on another device and silently removing a song that had been added back there. Now each save carries a random `saveId`, stored with the edit's audit entry; the owner's (and staff's) `GET /api/ev/events/:id` lists the last 20 as `recentSaveIds`. The keepalive notes its saveId and what it sent in the device copy; on the next load a copy whose keepalive arrived is rebased onto what it sent, so only changes made after it are restored (usually none: the copy is dropped silently). And when a device copy would be restored onto a server copy that changed since the copy's base, and would overwrite a field the server also changed, remove a song or announcement the server has, or (when its keepalive's arrival is unknown) add one back, nothing is saved: the page lists exactly what restoring would change, with "Restore these changes" and "Keep the saved version"; saving resumes after the choice. Restores onto an unchanged server copy still apply by themselves. The restore and merge notes name additions and removals, not only kept fields.
- **An upload that failed its check was described as "still being checked"**, and the form kept retrying it for minutes. The API now answers `audio_failed` (with the upload's id) for a failed or rejected upload, and `audio_not_ready` only for one still being checked. The form does not wait for a failed upload: it marks it in the Songs or Announcements list ("Upload failed — remove it"), says "Not saved: "<title>" failed its check. Remove it to save the rest.", and saves the details anyway (they are sent before the playlist); removing the item saves the rest at once.
- **The "Merged changes made in another tab" note never went away.** It now stays until the next save that sends a change of this tab's own without merging anything (a check that finds everything already saved does not count), or 10 seconds, and it is not shown when the only change was this tab's own keepalive arriving.
- **Closing a tab right after adding a song could lose the song, or delete a song saved on another device** (found in the third review). The keepalive sent the details PATCH and the playlist PUT as two separate requests, the PUT at a guessed version + 1. Browsers do not keep them in order: in about half the real-browser runs the PUT arrived first, was refused, and the song stayed only in that browser's device copy (so a request submitted from a phone missed it). Worse, if another device had saved once in the meantime, the PATCH was refused but the PUT's guessed version matched, and the tab's stale playlist replaced the other device's songs without a word. The keepalive is now **one request**, `POST /api/ev/events/:id/draft` (`SaveDraftRequest`: `version`, `expectStatus: "draft"` and `saveId` required, plus `details` and/or `playlist`), which applies the details and the playlist in one transaction against that one version: it lands whole or not at all. When it is refused, the device copy keeps the changes and the next load (or the tab coming back into view) merges them on top of the other device's work. The reopened page counts the keepalive as arrived only when its saveId is listed and it was made against the copy's own base.
- **A stopped tab kept saying "Nothing on this page was lost" after further edits.** When a tab learns (by catching up) that the request was submitted or approved elsewhere, it stops saving; if the member then keeps editing, the status now switches to "Your latest changes on this page were NOT saved."
- **"Your latest changes aren't saved yet, so the request was not sent" stayed after the save went through.** It now goes as soon as the next save succeeds.
- **Autosave could hit the 30-per-minute limit on changes** (a save can be a details PATCH plus a playlist PUT). Draft autosave now has its own limit of 120 per minute per client (`LIMITS.eventEdit` in `src/server/http/ratelimit.ts`): the keepalive's `POST /api/ev/events/:id/draft`, and `PATCH /api/ev/events/:id` / `PUT /api/ev/events/:id/playlist` whose body carries `expectStatus: "draft"`. The middleware reads those two requests' body (it already reads every body for the 1 MB cap) to tell: any other PATCH / PUT, such as a member's edit of a pending request (each posts an "edited" note to its Discord ticket) or an approved event, is also counted against the normal 30-per-minute limit (`limitNeedsBody` / `limitAfterBody`). Trusting the body is safe because the server refuses an edit that expects "draft" on any event that is not a draft (`409 status_changed`, nothing written, nothing posted to the ticket). Every other change stays at 30, and each edit is still signed-in, CSRF- and version-checked. The save delay is 1.5 s after the last change (was 1.2 s).
- **A tab hidden (not closed) right after an edit could undo newer changes made elsewhere when it came back** (found in the fourth review). The keepalive sent as the tab was hidden arrived, but the open tab did not know that: when it came back into view (or its next save was refused as out of date) it treated its own already-saved changes as unsaved and merged them again over the newer copy, so a host name changed on another device was set back and a song added back there was removed again, and both were saved. The same could happen after a normal save that reached the server but whose answer was lost. Now the tab keeps every save it sent until its answer comes back (the keepalive's never does), with what it sent. When a newer server copy lists that save's `saveId`, the tab first moves its base onto what the save sent, so only changes made after it count (usually none): the other device's work stays, nothing is sent, and the note names only what came in. A save that did not arrive still counts as unsaved and is merged on top as before. When it cannot be told (the event's list of recent saveIds is full and does not name it) and merging would overwrite work done elsewhere, the tab shows the saved version and asks, like a reopened page does ("Restore these changes" / "Keep the saved version"), saving nothing until the choice; its device copy is kept aside meanwhile, so closing the tab loses nothing. The reopened page and the open tab use the same rule for deciding whether a save arrived (`sortSaves` in `autosave.ts`, `rebaseForm` in `restore.ts`).

### Added
- **Upload right in the form:** "Upload a new announcement" in Announcements and "Upload a song" in Songs use the My audio upload (tus, MP3 ≤ 100 MB / WAV ≤ 250 MB from `GET /api/ev/config`, announcements ≥ 3 s, songs ≥ 30 s, the rights checkbox), attach it with `POST /api/ev/audio`, show the progress and then "Processing…" while the file is checked (polling `GET /api/ev/audio`), and when it is Ready select it for the announcement being created (added at once when its time is already chosen) or add it to the song list, which autosaves. A rejected file says why. Hidden with a note while uploads are switched off; a full My audio says so with a link. The upload code is shared with the My audio page (`src/events/components/upload.ts`), and both pages get the portal's tus chunk size (`src/app/ev/chunk.ts`).

## [0.5.2] — 2026-09-29 — Events: Liquidsoap-safe playlist names, start-kick rollback

Production incident, live test 2 on station 14 (2026-09-29 17:45 UTC): the start kick restarted the Event station with the event's playlists enabled; AzuraCast regenerated the Liquidsoap config and Liquidsoap refused it (`Error 2: Parse error`), `station_14_backend` went FATAL and the Event station was off the air for ~2.5 min until staff disabled the playlists by hand. The kick retried once into the same config, then gave up and left the station down.

### Fixed
- **Liquidsoap-safe playlist names, by construction.** AzuraCast writes each enabled playlist as the Liquidsoap variable `playlist_<short name>` (`ConfigWriter::getPlaylistVariableName` over `Strings::getProgrammaticString`), and `rawurlencode` leaves `~` alone, so the helper name `~EVT1 s1` became `playlist_~evt1_s1` — not an identifier. Pinned-song and announcement playlists are now **`EVT<id> s<n>`** and **`EVT<id> a<n>`** (ASCII, no `~`) everywhere names are built or recognised: `contract/paths.ts` (`pinName`, `annName`, `INTERNAL_NAME_RE`; the old `~EVT…` shape is only recognised as `LEGACY_INTERNAL_NAME_RE`, never built or sent), the wrapper's name checks (a playlist body with a `~` is refused), the build's orphan check and verify. Public titles still pass the strict sanitiser (no `~`), and a title shaped like a helper name (`EVT1 s1`, any case, spacing or separators, with or without `~`) is refused by create, staff booking and title edits with **400 `title_reserved`**; `mainName` falls back to `Event` for one already stored.
- **A rename is a supersede.** A build whose plan still names a legacy `~` playlist is never current: the start kick refuses to restart into it (alert: needs rebuild) and a rebuild re-applies it even at the same version. The rebuild creates the new-named playlists, moves the songs, then **DELETEs** the old registry playlists (never a PUT rename: the wrapper requires each playlist's recorded name). Production event 1's `~EVT1 s1`, `~EVT1 a1`, `~EVT1 a2` (ids 82–84, disabled by hand) go this way on its next **Build now**. Verify also reports a registry playlist that still carries a legacy name.
- **The start kick confirms the station came back, and rolls back at once when it did not.** After every `POST /backend/restart` the worker reads `GET /status` (5 s timeout) every 3 s and needs `backend_running` on consecutive reads spanning at least 12 s (a Liquidsoap that dies a few seconds in is caught), for at most 40 s of elapsed time — a hanging status endpoint cannot hold the kick. If the restart call fails or the backend is not running, it does NOT retry into the same config: it disables every registry playlist of the event, purges station 14's queue (the AutoDJ may already have queued a song from an event playlist — in the outage one kept playing after the manual disable and restart; every queued row is tried, failures are collected), restarts once more and confirms, and alerts "**start of event <id> failed — rolled back, Event station restored**" (or, when the purge failed, that the station restarted but its queue could not be purged) and tells the ticket. If that rollback restart does not bring the backend back, it pages "**EVENT STATION DOWN — manual action needed**" once and stops. **The event's status is the one record of a rollback:** it becomes `failed` (hidden on every public surface; staff see "**Failed — rolled back**" with an explanation). Start and end kicks act only on `built` / `live` events, so every other queued start kick of it (another version) skips; the end kick of a `failed` event keeps its playlists off and schedules the teardown, with no restart and no "ended" post. The only re-arm: staff **Build now** on a `failed` event sets it back to `built` and queues exactly one fresh start kick (at once inside the window) — a no-change Build now or autobuild rebuild of a built/live event never restarts. The write gate is checked before a rollback changes anything: with queues paused it pages "rollback needed … but queues are paused — nothing was changed" and changes nothing. A failed live re-kick (a staff-confirmed schedule change mid-event) says "**live event <id> taken off air — rolled back, Event station restarted without it**". **Verify never rolls back or writes:** a "not running" read is re-checked with the kick's own confirmation; still down → one "EVENT STATION DOWN" page; config errors in the log are alerted only. The off-air restart (end kick / on-air teardown: disable, then purge the queue, then restart) confirms the backend the same way and pages EVENT STATION DOWN at once when it is not running; while another event is inside its window it waits until 2 min after that event's end (bounded), never restarting over it; its one retry stays the only further restart. Bounded everywhere, never a restart loop.
- **The Liquidsoap log check knows the outage's shapes:** `Error <n>:` / `Parse error` lines and their `At line …, char …:` / `Unknown position:` position lines. A failed start records the log's errors and whether a new start banner appeared; verify reports "did not start (no start banner, backend not running)".
- **Dropdown lists were white-on-white** (music and events portals; e.g. /request "Kind of event"): `.input`'s translucent fill made Chrome on Windows paint the open option list white under the inherited cream text, so only the hovered option was readable. Selects now get an opaque dark fill (`#17171d`), options and optgroups the same fill with cream text, `color-scheme: dark` on every select, a CSS-only chevron (no `url()`), 44 px height (48 px on phones), a visible focus ring and the disabled state; `.ev-select` no longer forces the native look. `test/ui/select-style.test.ts` pins the rules and that every `<select>` carries `.input`.

### Tests
- `test/events-liq-names.test.ts` + `test/helpers/azuracast-liq.ts`: a TS port of AzuraCast's name → Liquidsoap variable pipeline (`getProgrammaticString` with mb_ereg's Unicode `\w`, `generateShortName`, `cleanUpVarName` with the HTML 4.01 entity table and RFC 3986 `rawurlencode`), pinned to station 14's real `short_name`s. Every helper name for event ids 1..99999 and n 1..200, main names from a hostile title corpus (Unicode, emoji, punctuation, `~`, `..`, quotes, HTML) plus 5000 seeded random titles, 20 000 random names over the wrapper's main-name charset and the compiler's own output all map to `/^[A-Za-z_][A-Za-z0-9_]*$/` (Unicode and ASCII `\w` variants). The old `~EVT1 s1` fails that check (`playlist_~evt1_s1`), and a `~` name cannot reach a playlist body.

Worker tests: confirmation with a supervisord flicker; a failed restart call and the incident itself (an enabled `~EVT42 s1`) roll back with exactly two restarts and the station restored; a song the AutoDJ queued from an event playlist is purged after the disables and before the rollback restart (and the off-air restart purges after disabling, before restarting); a 500 "Exited too quickly" rolls back without waiting; a rollback that cannot restore pages EVENT STATION DOWN once; a legacy build never restarts; supersede deletes 82–84-style playlists and the kick then airs the new ones; off-air restart into a down backend pages at once, two attempts, then stops. From two rounds of a fresh-context verifier's adversarial cases: two queued start kicks + a failing restart → exactly 2 restarts and one alert; a backend that dies after two running reads is rolled back; a `failed` event's end kick never restarts or posts "ended"; an off-air restart waits until 2 min after another event on air ends (`eventOnAirAt`, also tested on Postgres); a failed live re-kick's wording and silence afterwards; staff Build now on a `failed` event → exactly one more restart and it airs; a no-change Build now (or autobuild) on a live event → zero restarts, also after a re-arm; an event re-armed after a rollback whose later verify only logs config errors ends normally; queues paused during a needed rollback → nothing changed; verify with the backend down (also while paused) → one DOWN page and no writes; a single down read that recovers → nothing; a queue row that cannot be deleted leaves the others purged and no "restored"; a hanging status endpoint is bounded by elapsed time; `failed` is hidden publicly and Build now is allowed for it (API, DB and staff UI tests). The AzuraCast port no longer keeps ZWJ/ZWNJ (PHP 8.3 mb_ereg strips them). `test/e2e-events-kick.test.ts` replays the outage through the real containers. API: `title_reserved` before any database access and in the DB flow.

## [0.5.1] — 2026-09-29 — Events: EFM stingers show up

### Fixed
- **Flaky events e2e:** the test slot shift changed with the minute each test file loaded, so two suites could shift by different amounts and their day ranges overlapped (a 409 overlap on main's build of 58ec293). The shift is now constant for a whole run.
- **The announcement picker's EFM stingers were empty in production.** AzuraCast lists audio files as `type: "media"` in `files/list`; the events worker's `stinger_sync` only accepted `"file"`, so it stored none of the 12 stingers in `EFM Stingers/`. It now accepts `media` (and `file`), and the unit-test AzuraCast fake returns `media` like the real server, with a test that pins it.
- **The events worker speaks AzuraCast's real playlist-order, backend_options and schedule shapes; found by the first live build** (station 14: playlists 81/82 were built, then the order step failed with `unexpected_shape`). `PUT /playlist/{id}/order` now sends the `{entry id: weight 1..n}` map AzuraCast's `setMediaOrder` reads. Before, it sent a JSON list, which AzuraCast accepts with a 200 but applies to no row. The worker checks the echo and re-reads the order to confirm the change took. The wrapper refuses a list, and the map must still cover exactly the playlist's own fresh entries. `GET /order` rows are read as the array of entries AzuraCast returns. AzuraCast answers `backend_options: [""]` when a playlist has none; this is normalised to `[]` where playlists are read, so verify no longer reports a false difference. `event_registry.schedule_ids` come from the create answer, or from a fresh GET when the answer lacks them. They are refreshed after every full-body PUT, because AzuraCast replaces schedule rows sent without ids with new ones. Queue rows are addressed by their `links.self` (AzuraCast sends no `id`), so the kicks' queue purge works when the queue is not empty. The unit fakes and the harness mock now answer with these real shapes, and `test/azuracast-real.test.ts` parses captured station-14 answers (`test/fixtures/azuracast-real/`) with the client's own schemas.

## [0.3.5] — 2026-09-28 — Big songs are converted down to fit

A song that is too big for the portal's final-file cap is no longer rejected: the probe converts it DOWN so the final MP3 always fits. Owner decision (Jason): bitrate ladder 320 → 256 → 192 kbps CBR (libmp3lame), the highest rate that fits, 192 kbps at the lowest; a song that would not fit even at 192 kbps is rejected with its maximum length; an MP3 that already fits is never touched.

Why a cap at all: the worker ships the final file to AzuraCast's JSON `POST /files` route (base64 in JSON, nginx / PHP 50M body), which takes a final file of about 37.5 MiB. The portal's final-file cap `MAX_UPLOAD_BYTES` (35 MiB) and everything downstream of the probe (finalize, the worker's upload, the JSON route) are unchanged.

### Ladder math (`src/lib/fit.ts`, one shared module for the probe, web, worker, UI texts and tests)
- Audio budget = 35 MiB final cap (36,700,160 B) − 2 MiB cover (finalize's cover cap) − 16 KiB tag margin (title / artist / album / genre ≤ 200 UTF-16 units each + the APIC frame header: ~2 KB worst case, tested with node-id3) = **34,586,624 B**.
- Payload = budget − 16 KiB container margin (the LAME/Xing info frame, encoder padding frames, the info frame finalize's `-c copy` writes again) = **34,570,240 B**; duration × bitrate / 8 must fit it.
- Longest song per rate, `floor(payload × 8 / rate)`: **864 s (14.4 min) at 320k, 1080 s (18.0 min) at 256k, 1440 s (24.0 min) at 192k**. The duration cap `MAX_DURATION_S` is 1440 s for MP3 and WAV alike (was 20 min for MP3, 15 min for WAV).
- `pickBitrate(duration)`: the highest ladder rate whose max duration is ≥ the song's; `mp3FitsUntouched(size, id3Size)`: the file without its leading ID3v2 tag (which finalize strips and rewrites) ≤ payload and the whole file ≤ 35 MiB (finalize's input cap).

### Added
- **MP3 → MP3 re-encode in the probe** (`src/probe/transcode.ts`, `probe.ts`). An MP3 whose audio does not fit is decoded and encoded again, inside the same network-less sandbox as the WAV conversion, only after the magic gate (Layer III, no free format), the ID3 pre-scan and `ffprobe -f mp3` (one mp3 stream, only an attached picture besides, duration ≤ 24 min) accepted it: `ffmpeg -protocol_whitelist file,pipe -threads 1 -filter_threads 1 -vn -sn -dn -c:a mp3float -f mp3 -i … -map 0:a:0 -map_metadata -1 -map_chapters -1 [-ar 44100] -t 1445 -c:a libmp3lame -b:a <rate> -id3v2_version 0 -write_id3v1 0 -f mp3` under `prlimit` (256 MiB address space, no core) → `timeout` → `nice -n 19`, its own process group, argv only. Forced demuxer AND decoder; non-audio streams (the APIC picture) are discarded at the demuxer and never decoded; 44.1 / 48 kHz are kept, every other MPEG rate becomes 44.1 kHz; `-t` bounds the output whatever the header claimed. The output must pass as an upload would (magic, no ID3, `ffprobe -f mp3`, exactly the chosen CBR rate, duration within max(2 s, 2 %) of the original's, ≤ the audio budget) before it replaces the original under the same upload id (tmp + rename, re-hashed); tags and cover are pre-filled from the ORIGINAL file and written at finalize as before. New refusal codes `reencode_timeout`, `reencode_failed`, `reencode_invalid`, `reencoded_too_large`, each with a message.
- **WAV takes the same ladder** instead of a fixed 320k (`convertArgs(…, bitrate)`); the converted MP3 must fit the audio budget (was ≤ 35 MiB without the cover).
- **MP3 input cap 100 MB** (`MAX_MP3_UPLOAD_BYTES`), a new admin-lowerable cap `caps.maxMp3UploadBytes` (100 MiB ceiling), enforced like the WAV cap: tus creation by the declared type, `admitUpload` with the loaded caps, and the probe by the actual type (the request carries `maxMp3Bytes`); `mp3_too_large` now means over that cap. - **The re-encode rate comes from the counted frames, not the upload's header** (S2). ## [0.3.0] — 2026-09-27 — WAV uploads

Members can upload WAV files as well as MP3s. The network-less probe converts a WAV to a CBR 320 kbps MP3, which replaces the WAV under the same upload id; everything downstream (prefill, review, finalize with ID3 + APIC, the AzuraCast upload, the library, edit and removal requests) is unchanged and only ever sees that MP3. WAV only (no FLAC, AIFF or M4A).

### Added
- **Probe WAV path** (`src/probe/wav.ts`, `probe.ts`). The type comes from the magic bytes of the probe's private copy (`RIFF....WAVE`), never from the name or the declared type; RF64 / BW64 (`wav_rf64_unsupported`) and RIFX (`wav_unsupported`) are refused. A bounded RIFF chunk walk runs in JS before any parser: every chunk inside the RIFF and the RIFF inside the file (a truncated file or a lying RIFF / data size → `wav_truncated`, more than 64 KiB after the RIFF → `wav_trailing_data`), at most 64 chunks, exactly one `fmt ` before exactly one `data`, a LIST ≤ 1 MiB whose INFO items tile it exactly (`wav_bad_list`; music-metadata reads every INFO value into memory), other chunks ≤ 16 MiB, at most one `id3 ` chunk, which gets the MP3 tag's pre-scan (≤ 5 MB, no compressed / encrypted frames). PCM only: integer 8/16/24/32-bit and float 32/64-bit, plain or WAVE_FORMAT_EXTENSIBLE with the PCM / IEEE-float GUID; ADPCM, MP3-in-WAV, A-law, µ-law, GSM and anything else are `wav_codec_unsupported`. 1–8 channels, 8–192 kHz, a consistent block align and byte rate, 30 s to 15 min. `ffprobe -f wav -protocol_whitelist file,pipe -threads 1` must agree with the header (one audio stream; only an `id3 ` APIC may appear as an attached picture; same channels, rate and duration ±1 s). music-metadata (heap-capped child, parser chosen by the copy's `.wav` name) pre-fills title / artist / album / genre / year from LIST/INFO and the `id3 ` chunk through the same `clipTag`; an APIC takes the same hardened cover path. The conversion is `ffmpeg -f wav … -map 0:a:0 -map_metadata -1 [-ac 2] [-ar 44100|48000] -c:a libmp3lame -b:a 320k -threads 1` under `prlimit` (256 MiB address space) → `timeout` (300 s) → `nice -n 19`, in its own process group. The MP3 is then checked like an upload (magic + second frame, no ID3, `ffprobe -f mp3`, exactly 320 kbps, duration within 1 s of the WAV's, ≤ 35 MB) before it replaces the WAV (tmp + rename, re-hashed); the cover is published last.
- **Upload caps by type.** New cap `maxWavUploadBytes` (250 MB; admins may lower it). The tus creation is capped by the type its Upload-Metadata `filetype` declares (audio/wav, x-wav, wave, vnd.wave → WAV; anything missing, malformed, repeated or else → MP3): the route checks the compiled limits (`413 upload_too_large` / `wav_upload_too_large`), `admitUpload` the loaded caps; tus `maxSize` is 250 MB. The probe request carries the loaded WAV cap (`maxWavBytes`, optional in the schema) and the probe caps by the ACTUAL type: an MP3 over 35 MB is `mp3_too_large` whatever it was declared as, a WAV over the WAV cap `wav_too_large`.
- **Staging accounting.** A WAV counts at its full length toward the per-user in-flight and the global staging caps; when the worker collects a converted result (`inputFormat: 'wav'`) it re-charges the upload row at the MP3's size in the same transaction as the item's move to pending. `items.input_format` records `mp3` / `wav` (migration `0006_v030_wav_input`).
- **UI.** The submit page accepts `.wav` / audio/wav / audio/x-wav / audio/wave, checks each file against its own type's limit, declares the type to tus, says "converting it to a 320 kbps MP3" while a WAV is checked, and shows "Converted from WAV (320 kbps MP3)" on the item (submit and review pages). Every WAV rejection code has a human message (`messages.ts`).

### Changed
- **A rejected upload's bytes are deleted at once.** On any refusal the probe unlinks the staged upload (and any cover it had published for it) and reports `released: true` (optional in the failure schema); the worker marks the upload `expired`, releasing its bytes from the staging quota. Before, a refused upload stayed on disk and counted toward the global staging cap for 7 days, which a 250 MB WAV would make a cheap way to fill staging. A failure without `released` keeps the old behaviour (an interrupted probe is released too, see Review fixes).
- The probe's `sha256File` and `publishFile` stream in 1 MiB steps (no whole-file buffers in the 256 MB probe) and `sha256File` no longer follows a symlink. `runLimited` takes an optional `nice` (1–19), placed between `timeout` and the tool (`/bin/nice`, busybox).
- An MP3 over 35 MB is now refused `mp3_too_large` after the magic check (it was `input_size` from the copy); `input_size` now means empty or over the hard 250 MB input cap.

### Review fixes (before release)
- **Bytes after the RIFF are checked, not skipped.** ffmpeg's wav demuxer ignores the RIFF size and parses chunks to the end of the file (music-metadata stops at the RIFF end), so an `id3 ` chunk (zlib bomb), a second id3 chunk, a LIST/INFO or `bext` appended after the RIFF reached ffmpeg unchecked. The chunk walk now runs to EOF: the ≤ 64 KiB after the RIFF must be all zero, or chunks under exactly the rules inside it (shared chunk count, single `fmt ` / `data` / id3 chunk, LIST/INFO tiling, id3 pre-scan); a header straddling the RIFF end counts as after it; anything else is `wav_trailing_data`.
- **One ID3 tag per `id3 ` chunk.** ffmpeg's ID3v2 reader keeps reading tags after the first (and skips over a header of an unsupported version by the length it declares, so a following chunk named `ID3x` could chain to an unscanned tag). The rest of the chunk after the tag must be zero padding, and the 10 bytes where ffmpeg looks for a next tag (after the tag, and after a v2.4 footer) must not look like an ID3 header, wherever they are (`wav_bad_id3`).
- **Interrupted jobs leave nothing behind.** At start-up the probe removes the per-job dirs (`p-` / `f-` / `a-`) a restart mid-job left in `staging/work` (a WAV job's private copy is up to 250 MB + the MP3, outside the staging quota). An interrupted in-web `probe` is now answered as a `probe` failure `interrupted` with its upload released (deleted before the result is written; nothing is done for a request that already has a result), so the worker marks the upload `expired` instead of holding its bytes until retention.
- **Unfinalized WAVs get their own reason.** A RIFF size of 0 / 0xFFFFFFFF or a data size of 0xFFFFFFFF (a file written to a pipe or by a live recorder, e.g. `ffmpeg … -f wav pipe:1`) is still refused, now as `wav_unfinalized` with a message that says re-exporting fixes it, instead of `wav_truncated`.
- **Size texts follow the loaded caps.** `upload_too_large` / `wav_upload_too_large` shown by the submit page carry the loaded (possibly admin-lowered) limits; the generic texts and `wav_too_large` no longer name a number. `interrupted` has a message.
- **Probe CPU weight.** `music-probe` gets `cpu_shares: 256` (cgroup v2 weight ~10 vs ~39 for a default container), so a conversion and the copy / hash / publish around it yield to the Discord bots; `nice -n 19` on ffmpeg only orders processes inside the probe's own cgroup.

- **Stuck archive rows are settled by the portal itself (#1).** New mutating job kind `reconcile_archive` (in `JOB_KINDS`, `MUTATING_JOB_KINDS` and the request runner; scan window, pause and write gate as every other write). A scheduler sweep (every 10 min) queues it for `archiving` / `restoring` rows untouched for 30 min (new `archive.updated_at`, set on every status write and when a re-run resumes the row) that no queued or running `archive` / `restore` job will pick up. Where the file actually is decides: `archiving` with the file at `Removed/<id>/…` → the archive is finished (row `archived`, `after_archive` snapshot, re-verify; its removal request, even one the failed attempt already marked failed, is applied); `archiving` with the file still in the library → the snapshot memberships are merged back, the row is closed `failed` and an open request fails `archive_rolled_back`; `restoring` with the file still archived → back to `archived`; `restoring` with the file back → the restore is finished; anything else (media id gone, file elsewhere) → an alert naming the paths. Every outcome alerts.
- **Managers see and act on such rows (#1).** `GET /api/archive` and the Archived songs page list `archiving` rows too, with their `status`. New `POST /api/archive/:id/reconcile` (manage; `409 not_in_progress`, `409 archive_job_pending`) runs the reconciler now (**Resolve** button); `POST /api/archive/:id/restore` on an `archiving` row settles it first and then restores an archived song.
- **An open archive blocks other mutations of the song (#2).** While a media has an `archiving` / `restoring` row, `apply_edit`, `move`, `set_playlists`, `apply_art`, `reverify` and the ingest verify wait (`RetryLater` / `Defer`, no attempt spent, the default 7-day age bound) instead of editing, moving or repairing a half-archived song; the manager edit / playlist / art endpoints answer `409 archive_in_progress`. Since the reconciler closes stale rows, a later archive always starts with a new row and a fresh `before_archive` snapshot, never a closed attempt's. The archive rollback now MERGES the snapshot memberships (a REPLACE would drop memberships added since) and works wherever the file is in the library.
- **Events refusal on resume (#3).** A resumed archive repeats the `in_events_playlists` check before any further write: a membership outside the station set that appeared between attempts puts the snapshot memberships back, closes the row and refuses. The same check runs on the cleared state right before the move.
- **Only applied snapshots supersede (#4).** Supersede (re-verify chains and the ingest verify) and lost-row recovery consider only `after_*` and `ingest` snapshots (`APPLIED_SNAPSHOT_REASONS`); the `before_*` snapshot of an operation that then failed or was refused no longer marks older chains done unchecked, and recovery never re-applies it. `apply_edit` takes its `after_edit` snapshot also when it queues the folder move (the metadata change applied), so an older chain cannot revert it before the move runs.
- **First-sync playlist ids (#5).** The very first library sync marks every observed id that is neither assignable/default nor foreign as unconfirmed (so an admin can still move it to `foreign_playlist_ids`) and alerts once, like later syncs.
- **Orphan hint (#6, accepted residual).** An upload refused only by the time check (e.g. clock skew) is probably the item's own earlier upload: the alert now names that file (path and media id) and says to delete it by hand once the new upload is live.
- Migration `0005_v022_archive_reconcile` (`archive.updated_at`, default `now()`).
- Mock AzuraCast: `/__mock/az/station14` sets a file's Events (station 14) memberships, as that station's own UI would.

**Deploy note:** the first-sync change applies only while `station_playlist_ids` is still unset. If v0.2.1 already ran a library sync in production, the ids it classified silently stay confirmed; to make them movable to foreign, set `unconfirmed_playlist_ids` by hand to the `station_playlist_ids` values that are not in `assignable_playlist_ids` / `default_playlist_ids` (the sync keeps that list from then on). Do not reset `station_playlist_ids` to `null` on a live system: every playlist job fails `station_playlist_ids_unset` until the next sync.

### Web / probe / CI (PR #26 checks)
- **Request bodies are complete and the 1 MB cap is deterministic.** Next 15.5 runs Node middleware on a clone of the body and swaps the buffered copy into the request without awaiting it, so a handler that started reading while the body was still arriving lost its start: an oversized chunked body could answer 400 `invalid_json` instead of 413 (the CI flake), and a slow valid body 400. The middleware now reads its copy of every unsafe request's body to the end, counting it against the cap (413 `payload_too_large`, `Connection: close`), after the rate-limit and CSRF refusals; handlers keep their own caps. Regression test sends the body with a gap.
- **Probe children run without a shell.** `runLimited` execs `prlimit --as=<bytes> --core=0 -- timeout -s KILL -k 1 <s> <tool> <args...>` as a plain argv (same RLIMIT_AS / no-core limits as the former `sh -c 'ulimit ...'`); probe and test images add `util-linux-misc` (CodeQL js/shell-command-injection-from-environment).
- **Linear SVG sniff.** The cover SVG check is a cursor scan instead of a regex that backtracked exponentially on a run of comments (CodeQL js/redos; a 1 KiB head of `<!---->` hung the probe). A comment now ends at its first `-->`.
- **gitleaks:** repo-root `.gitleaks.toml` keeps the default rules and allowlists the verified false positives by exact path, on `generic-api-key` / `discord-client-id` only.

## [0.2.1] — 2026-09-27 — v0.2.0 verification fix round

### Worker
Fixes for the confirmed worker / AzuraCast findings of the v0.2.0 verification: ways a song could be silently lost from rotation, stranded in `Removed/`, attached to the wrong file, or have a manager's change reverted.
- **Ingest never adopts a row it did not upload (ING-1, SEC-4).** The target path is reserved (`ingest_runs.target_path` + new `upload_attempted_at`, DB clock) only after the window and pause checks, right before the POST. Other active runs' reservations count as taken in the collision walk (and a partial unique index on `ingest_runs.target_path` for non-terminal runs backs it). A retry adopts the row at its reserved path only when it is provably its own upload: attempt marker set, a scanned media row whose file size equals `final.mp3`'s, uploaded no earlier than the attempt, length within 2 s of the probe duration when known, and no other item or run holding the media id; anything else is audited, alerted and skipped (the next ` (n)` name is used).
- **Archive is resumable (ARC-1, ARC-2).** An `archive` row with status `archiving` and the `before_archive` snapshot is written before the first AzuraCast write; a re-run reuses that snapshot and continues from where the file really is. A move whose reply is lost (timeout, failed verify read) finishes the archive when the file is at `Removed/<id>/<name>`; only a verified not-moved file is rolled back (and the row closed as `failed`).
- **Restore is resumable (RES-1).** Status `restoring` is written before the move; a re-run with the file already at its original path (same `unique_id`) skips the move and continues with metadata, memberships (merged), verify and the status flip. `Restore` is offered for `restoring` rows.
- **Re-verify never reverts newer changes (VER-1).** A reverify re-applies its snapshot only while it is the latest portal snapshot of the media (else it is marked superseded and the request done), re-adds missing playlist ids by merge (never a REPLACE with an old set), and counts extra memberships as fine. `set_playlists` now takes an `after_playlists` snapshot and runs its own reverify chain. Lost-row recovery uses the latest snapshot. The ingest verify and repairs merge too, and a portal mutation of a still-verifying song supersedes the ingest verify (the song goes live) instead of being treated as lost.
- **Events playlists (ARC-3).** A song with a membership in any playlist outside the station-1 set (the Events station 14) is refused before anything changes (`in_events_playlists: <ids>`, and the ticket says to take it out of those playlists first); the "cleared" check counts station-1 memberships only. `foreign_playlist_ids` default is now `[74, 75, 76, 77, 78]` (live DB).
- **Station playlist ids are sync-owned (SET-1).** `station_playlist_ids` is read-only in the admin UI/API; `foreign_playlist_ids` is the admin control. The sync never shrinks the set by observation; a newly seen id that is neither known nor foreign is counted as station 1, alerted once and recorded in `unconfirmed_playlist_ids`. Admins cannot mark an assignable/default or a confirmed station-1 id foreign, nor make a foreign id assignable.
- **Waits (JOB-1, F1).** Scan-window and pacing waits are `exact` (no 30-minute age floor that phase-locks old jobs onto the closed window). A wait that ages out now fails its request (`failRequest`, `wait_expired`, ticket post) or item (`failIngest`) instead of only killing the job; window / on-air / pacing and the ingest job's own waits get an explicit 40-day bound (past the 30-day artist wait), `ingest_verify` keeps 7 days.
- **Smaller fixes.** A manager's direct edit carries the artist the manager saw (`beforeArtist`), so a retry after the metadata PUT still queues the folder move (EDIT-1). Recovery remaps queued jobs' `payload.mediaId` in the same transaction (REMAP-1). An edit whose new artist sanitizes to another artist's folder (active, pending or denied) fails with `artist_folder_taken` instead of merging into it (SEC-5).
- **Album-art verify (ART-1).** The wrapper gains a read-only, station-checked `GET /api/station/{id}/art/{media_id}` (`getArt`, never follows the generic-image redirect; the path is already in the contract drift probe). `apply_art` stores the old art's sha256 in the `before_art` snapshot and, after the upload, requires the served art to be the probe JPEG or a complete JPEG with the probe's dimensions (AzuraCast re-encodes).
- Migration `0004_v021_worker` (`archive_status` += `archiving`, `restoring`; `ingest_runs.upload_attempted_at`; the two partial unique indexes). It fails if two active runs already share a `target_path` or a media has two open archive rows.
- Mock AzuraCast: Events playlists 74–78 are station 14's (the playlist REPLACE keeps exactly those); list entries report the file size; uploads get a real `mtime`/`uploaded_at`; stored art is re-encoded when its header is readable; `/__mock/az/ignore-next-put` (a metadata PUT that reports success without storing; F2 test).

### Web / probe / deploy

#### Security
- **Album-art uploads cannot exhaust music-web's memory (SEC-1).** `POST /api/uploads/art` now takes an in-flight slot (1 per member, 3 per process; `429 art_upload_in_progress` / `503 art_uploads_busy`) and runs the quota pre-check before reading any body byte; those refusals, like the route's earlier ones (rate limit, sign-in, uploads paused) and every CSRF refusal, carry `Connection: close`. The body is read into one buffer of its `Content-Length` (required: `411 content_length_required`; still ≤ 5 MB + 64 KB) and the single multipart file part is parsed in place (`server/art/multipart.ts`) instead of through `Response.formData()` + `File.arrayBuffer()` (about four copies per request before). A body still incomplete after 120 s is `408 body_timeout`, a disconnect ends the read, and the slot is released in `finally`. Worst case about 15 MB of art bodies in flight.
- **Album-art caps (SEC-2).** Per member per rolling 24 h: 30 uploads and 50 MB (`429 art_daily_quota`); globally 512 MB of processing + ready art (`503 art_storage_full`). Art bytes (processing, and ready JPEGs kept 7 days, charged at the uploaded size) now count toward `maxStagingBytes` for both art and tus admissions, all under the one staging advisory lock; the art row is inserted by that locked admission before the raw file is written, and any later failure (file write, audit, spool request) marks it rejected and removes the raw file (best effort, never masking the original error). New caps `artUploadsPerUserPerDay`, `artBytesPerUserPerDay`, `maxArtBytes` (admins may lower them; optional in the admin schema so older saved caps stay valid).
- **One metadata character rule (SEC-3).** `PATCH /api/items/:id` uses the edit-request rule (`requests/common.ts` `metaText`: NFC, trimmed, length counted after NFC, no `\p{Cc}` incl. `\n`/`\t`, no `\p{Cf}`, no U+2028/U+2029). A newline or tab accepted here used to fail finalize after approval (`bad_finalize_request`), and bidi / zero-width characters reached the on-air ID3. The probe's pre-fill (`probe/tags.ts` `clipTag`) turns controls and separators into a space, drops `\p{Cf}`, applies NFC and never cuts a surrogate pair, so an untouched pre-fill always finalizes.

#### Deploy
- **`MUSIC_APP_DB_PASSWORD` must be URL-safe (F1):** 24–128 characters of `[A-Za-z0-9_.-]`; `/`, `+` and `=` (base64) are refused because the same value goes into `DATABASE_URL`. Generate it with `openssl rand -hex 24`. **Upgrade note:** a deployment whose password contains `+` or `=` (which the URL tolerated) must rotate it in `migrate.env`, `web.env` and `worker.env` before this migrate step runs.
- **First boot cannot race initdb (F2):** the `music-db` healthcheck uses TCP (`pg_isready -h 127.0.0.1`), which the entrypoint's socket-only initdb server does not answer, and `music-migrate` retries its first connect for up to 60 s on "not reachable / starting up" errors only (a bad password or SQL error still fails at once).
